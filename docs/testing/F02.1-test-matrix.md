# F02.1 test matrix

**Executed:** 2026-11-20
**Commands:** `bash scripts/verify-f02-1.sh`, `node scripts/check-contrast.mjs`,
and a real browser against the running Docker stack
**Environment:** Windows 11, Docker 29.5.3, Node 22.20.0, Chromium, PostgreSQL 17-alpine

## What is scripted and what is not

Eighteen checks are scripted and can run unattended: the login lifecycle through the
same-origin proxy, route protection, the role gate, session expiry, logout,
and that no seeded credential appears in the shipped markup.

Five are interaction behaviour - focus trap, focus return, double submit,
inline validation, layout at six widths. **A browser is the only honest way to
check those**, so they are recorded here with the values that were measured
rather than as ticks, so the next person can re-run them and compare. Nothing
re-runs them automatically; that is risk R-23, carried deliberately with
Playwright named as the answer and F07 as the trigger.

Contrast is a third category: computed from the token values by
`scripts/check-contrast.mjs`, which is committed so the numbers stay
re-checkable rather than becoming a claim.

### F02.1-T15 - the backend being down is explained, not hidden

This one was **reported as a failure first, and the failure was real** - but not
where the check was looking.

`getCurrentUser()` deliberately returns early when there is no cookie:

```ts
if (!token) return null;   // No cookie at all: skip the round trip entirely.
```

The check requested `/login` without a cookie, so nothing was probed, no
`ApiUnreachableError` was thrown, and the page rendered normally. The early
return is correct - probing the API on every anonymous login-page view to
detect a rare condition is a cost on the common path.

What it exposed is that **a visitor with no cookie finds out only on submit**,
and at that point the proxy's `502` fell into the generic branch:
*"Something went wrong signing you in. Please try again."* That is the retry
loop the code's own comment says it exists to avoid.

So the fix was in the product, not the assertion: `502`, `503` and `504` now
produce *"Could not reach the server. It may be starting up or down."* And the
check was split, because there are two visitors and two paths.

The last four rows need **3.0**, not 4.5: WCAG 1.4.11 governs the visual
boundary of a user interface component and the focus indicator, which is a
different requirement from 1.4.3 text contrast. `--color-border` (`#E2E8F0`,
**1.18:1**) is used only for decoration, where neither applies.

**Four tokens were changed because of this script**, three of which had been
sitting within 0.1 of the threshold: secondary text 4.55 → 5.27, success
4.57 → 6.49, warning 4.51 → 6.37, danger 5.30 → 6.80.

## What is not covered

- **No automated interaction test.** Risk R-23. The five browser rows above
  would not catch a regression on their own; they have to be re-run by hand.
- **No dark mode**, so no dark-mode contrast run.
- **No screen-reader pass with a real screen reader.** The semantics are
  verified through the accessibility tree (`role="menu"`, `aria-invalid`,
  `aria-describedby`, `aria-current`), which is what the browser exposes to
  one - not the same as hearing it.
- **No visual regression testing.** Deliberate: at four screens it would
  produce more maintenance than signal.
