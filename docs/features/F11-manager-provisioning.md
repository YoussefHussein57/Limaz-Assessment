# F11 - Company manager provisioning

Closing R-32. A company can now be taken from "created" to "somebody can sign
in and resolve its reviews" entirely through the application.

**This is an owner-requested enhancement, not an assessment requirement.** The
brief asks for two *seeded* companies with a manager each, and those have
existed since F01. It does not ask for manager creation. F11 exists because
the gap it closes was the most visible thing wrong with the admin panel.

---

## 1. What was built

### Backend - two routes, on the existing admin controller

| Route | Purpose |
|---|---|
| `GET /v1/admin/companies/:companyId/managers` | Safe metadata, bounded at 100 |
| `POST /v1/admin/companies/:companyId/managers` | Create one manager, 201 |

**No migration.** The `User` model already had everything: a nullable
`companyId` with a CHECK constraint that forbids a manager without one, a
globally unique email, a `passwordHash`, and a `UserRole` enum. Adding a
column would have been inventing a requirement.

### Frontend - one panel

A Managers panel on the company detail page, above the API keys, with an
accessible dialog. The company-without-manager warning now points at it
instead of ending in "this version does not automate that".

## 2. The two fields the caller cannot set

This is the whole security story of the feature.

```
role      -> always MANAGER, written by ManagerAdminService
companyId -> always the company in the PATH, after the role check
```

Neither appears in `createManagerSchema`, which is `.strict()`. So a body
carrying one is a **400 that creates nothing** - not a field that is parsed
and then ignored.

The difference matters more here than anywhere else in the codebase. "Ignored"
is a property of today's code: it depends on nobody ever spreading the parsed
object into `prisma.user.create`. "Refused" is a property of the schema, and it
holds whatever the service does next.

| Attempt | Answer | Test |
|---|---|---|
| `"role": "PLATFORM_ADMIN"` | 400, no row created | F11-T10 |
| `"companyId": "<another company>"` | 400, no row created | F11-T11 |
| A typo in a field name | 400 | F11-T09 |

| Caller | These routes |
|---|---|
| Platform admin | ✅ |
| Company manager | 403 `insufficient_role` (F11-T17) |
| A manager created *by* this feature | 403 - no privilege ladder (F11-T16b) |
| Company API key | 403 `caller_type_not_allowed` (F11-T18) |
| Unauthenticated | 401 (F11-T19) |
| Missing `x-limaz-client`, or a foreign `Origin` | 403, nothing created (F11-T20) |

## 3. The password

### Chosen by the administrator, not generated

Both shapes were available and the choice is not obvious, so here is the
reasoning.

**Generated by the server** would mean returning a plaintext credential in the
response, with everything that implies: `Cache-Control: no-store`, a one-time
reveal dialog, and a lost response leaving an account nobody can sign in to.
That machinery already exists for API keys, so it was not the cost.

**Chosen by the administrator** wins because *somebody has to carry the first
password out of band either way* - this deployment sends no email. Having the
administrator choose it means the response carries **no credential at all**:
nothing to leak into a proxy log, an error reporter or a devtools panel, and
no reason for a `no-store` header on this route.

### What is stored, and what is refused

```ts
const passwordHash = await this.passwords.hash(input.password);
```

The **same** `PasswordService` login verifies against. A second hashing path
would mean an account that cannot sign in with the password it was created
with. Verified structurally: F11-T12 asserts the stored value is a bcrypt
digest and contains no part of the plaintext, and F11-T14 signs in with it.

| Bound | Value | Why that number |
|---|---|---|
| Minimum | 12 characters | This endpoint **sets** policy for a new credential. Login's bound is deliberately loose because a "too short" answer there would confirm an address exists |
| Maximum | **72 bytes** | bcrypt hashes at most 72 bytes and silently discards the rest. Accepting more would create an account with far less entropy than the person believes they set, and nothing would say so (F11-T08b) |

The maximum is on **bytes**, not characters, because that is what bcrypt
counts - a 40-character Arabic passphrase is already over the limit in UTF-8.

### Where it goes in the browser

Typed into a real `type="password"` input with an accessible show/hide toggle
whose label names the action it will perform. Cleared from component state on
success and on close. Verified in the browser after a successful creation:
both storages empty, nothing in the URL, and the value absent from the DOM.

## 4. The email

Lowercased and trimmed with the **same transform `loginSchema` applies**, and
that is the point rather than a detail. If the two diverged, this endpoint
would cheerfully create an account whose address nobody could type: login
lowercases what the person entered, the stored value keeps its capitals, and
the unique index never matches.

```ts
.string().max(320).trim().toLowerCase().pipe(z.email(...))
```

**Piped, not chained.** `.trim()` and `.toLowerCase()` are transforms;
`z.email()` is a separate schema. Written the other way round the format check
runs against the raw input, and ` Nour@Example.com ` - what a person actually
pastes - is refused for the whitespace it was about to have removed. That is
exactly how it was first written, and F11-T07 caught it.

### Uniqueness is global, and stays that way

One `@unique` on `User.email`. Login takes an email and a password with **no
company selector**, so an address that identified two users would make login
ambiguous. F11-T06c asserts the same address is refused in a second company.

The duplicate is caught from the **database**, not before the insert:

```ts
catch (error) { if (P2002) throw new ConflictException(...) }
```

There is no pre-check at all. A check-then-insert loses the race when two
administrators submit the same address at the same moment - both SELECTs find
nothing, both INSERTs run, and one raises 23505 from a path that was not
expecting it, which is how this becomes a 500. F11-T06d sends two genuinely
concurrent creations and asserts `[201, 409]` with exactly one row.

## 5. What closing R-32 actually required

A 201 is not evidence. F11-T22 is:

1. create a manager through the API
2. sign in as that account
3. submit an expense with the company's **own API key**, over its policy limit
4. the real policy engine opens a review
5. resolve it as the new manager
6. assert in PostgreSQL that `resolvedByUserId` is the account that did not
   exist when the test started, `resolvedAt` is set, and the expense's
   `decision` is still `REVIEW` while its `status` is now `APPROVED`

The same sequence was then driven through the browser: a company with no
manager, two managers added through the dialog, mixed-case email normalised,
a duplicate refused with a readable message, and the new manager signed in to
their own workspace.

## 6. What was NOT built

| Not built | Why |
|---|---|
| Password change or reset | No email delivery, and an administrator-set replacement is a route that overwrites a credential. Recorded as **R-36** and stated in the UI |
| Forced change on first sign-in | Would be a claim the system cannot honour |
| Deactivation or deletion | A resolved review names its reviewer. Deleting that user is a referential and an audit problem, and `onDelete: Restrict` already refuses it |
| A role editor | Changing a role is a privilege change, not account administration |
| Creating a platform administrator | The only role that can create accounts. A route that mints one is a privilege ladder |
| Transfer between companies | A manager's past reviews belong to the company they were in |
| Employee accounts | Employees are identifiers on expenses, not users of this system |
