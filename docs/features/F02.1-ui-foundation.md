# F02.1 - UI foundation, authentication screens and app shell

**Status:** Implemented, awaiting project-owner approval
**Date:** 2026-11-20
**Depends on:** F00, F01, F02
**Blocks:** F06, F07, F08

## Objective

A person can sign in, see who they are and which company they belong to, move
around an application shell that works from 360px upward, and sign out. Every
convention F06, F07 and F08 will follow is decided and demonstrated here on
one real screen rather than asserted in a document.

## Scope

### In scope

- Design tokens, typography and a self-hosted font
- Seven primitives: Button, Field, Badge, Alert, Card, Spinner, Skeleton
- App shell: sidebar at `lg`, drawer below it, user menu, page header, skip link
- Login page, server-side route protection, role gate, logout
- Server-resolved identity through the same-origin proxy
- Two honest placeholder workspaces - manager and platform admin
- 23 acceptance checks: 18 scripted, 5 browser-verified
- `scripts/check-contrast.mjs`, committed so the numbers stay re-checkable

### Out of scope, deliberately

Expense lists, review queues, policy editors, company administration, charts,
any invented figure, dark mode, internationalisation, a component library
dependency beyond the two Radix primitives named below.

## Architecture

The conventions are written up in [`docs/architecture/frontend.md`](../architecture/frontend.md).
This document records the decisions and what was measured; that one is what a
person adding a page reads.

### Identity is resolved on the server

`app/(app)/layout.tsx` is a Server Component. It reads the `HttpOnly` session
cookie, forwards it to `GET /v1/auth/me`, and redirects on 401. The browser
never sees a shell rendered before the server knows who is in it.

Three alternatives were rejected, each for a concrete reason rather than
taste - a client Context with `useEffect` (guaranteed flash, request waterfall),
TanStack Query for identity (same, plus a dependency with nothing to cache;
it arrives in F06 where there is real server state), and Next middleware
(can see only that a cookie *exists*, which is a presence check dressed up as
security).

### None of the routing is security

The API answers 401, 403 and 404 on its own merits whatever the browser
believes, and F02 proves each of those without a browser involved. The
redirects exist so a person is not left looking at an empty frame; the hidden
navigation exists so nobody is shown a door that will not open.

**Adding a page does not protect it. Protecting it happens in the API.**

That sentence is in the architecture document, in `lib/auth.ts`, and here,
because it is the single thing most likely to be misread by whoever adds the
next page.

## What was measured, not assumed

### Contrast

`node scripts/check-contrast.mjs` prints the ratio of all 15 token pairs and
exits non-zero on a failure. **Four tokens were changed because of what it
printed**, three of which sat within 0.1 of the AA threshold:

| Token | Was | Is | Measured |
|---|---|---|---|
| secondary text | `#64748B` | `#5A6A80` | 4.55 → **5.27** |
| success text | `#15803D` | `#166534` | 4.57 → **6.49** |
| warning text | `#B45309` | `#92400E` | 4.51 → **6.37** |
| danger text | `#B91C1C` | `#991B1B` | 5.30 → **6.80** |

A ratio of 4.51 passes WCAG AA until a different tool rounds differently. The
margin is the point.

### Two border tokens, because 1.4.11 is not 1.4.3

| Token | Value | On background | On surface | For |
|---|---|---|---|---|
| `--color-border` | `#E2E8F0` | **1.18:1** | 1.23:1 | cards, dividers, table rules |
| `--color-border-input` | `#64748B` | **4.55:1** | **4.76:1** | the boundary of a form control |

WCAG 1.4.11 requires 3:1 for the visual boundary of a user interface
component - the edge that tells you where an input begins. It does **not**
apply to a decorative rule. One token for both would either fail the inputs or
make every card edge heavy.

### Widths

Checked in a real browser, not inferred from classes:

| Width | `scrollWidth` vs viewport | Sidebar |
|---|---|---|
| 360 | 360 / 360, no overflow | drawer |
| 390 | no overflow | drawer |
| 768 | no overflow | drawer |
| 1024 | no overflow | `display: flex` |
| 1440 | no overflow, content capped at **1152** | visible |
| 1920 | no overflow, content capped at **1152** | visible |

`lg` (1024) rather than `md`: at 768px a 260px sidebar leaves about 500px of
content, too narrow for the expense table F06 puts there.

## Two Radix primitives, and only two

| Component | Built on | Why |
|---|---|---|
| Button, Field, Badge, Alert, Card, Spinner, Skeleton | nothing | No behaviour worth a dependency |
| `MobileNav` | `@radix-ui/react-dialog` | Focus trap, Escape, focus return, scroll lock, inert background |
| `UserMenu` | `@radix-ui/react-dropdown-menu` | Roving arrow-key focus, Escape, focus return, `role="menu"` |

Each of those behaviours is easy to get subtly wrong, and wrong makes the
drawer unusable for exactly the people the requirement exists to serve. A
hand-rolled focus trap is a week of bugs found by other people.

Verified rather than claimed: with the drawer open,
`{ drawerOpen: true, bodyScrollLocked: true, focusInsideDrawer: true }`, and
Escape returned focus to `"Open navigation menu"`.

There is no `clsx` and no `tailwind-merge`. `lib/cn.ts` is six lines, and every
call site is ours, so no conflicting utility classes arrive from outside to
resolve.

## The double-submit guard is a ref, and the reason is visible

```ts
const inFlight = useRef(false);
if (inFlight.current) return;
inFlight.current = true;
```

Five synchronous clicks on the submit button produced **one** login request.
In the same measurement, the button's `disabled` attribute read `null`
immediately after the clicks - React had not re-rendered yet.

That is the whole argument. A `disabled` prop driven by state closes the door
on the next render; a ref closes it in the same tick. On a slow connection the
state version sends two logins and the second one races the first.

## Decisions that cost something

| Decision | Cost | Why anyway |
|---|---|---|
| Server-resolved identity | `force-dynamic` on protected routes - no static generation | A flash of the wrong shell, or of someone else's name, is worse than a render |
| `/login` outside `(app)` | A route group that looks redundant | Inside it, an expired session redirects to a page that fails the same check and redirects again. Structure beats a conditional somebody has to remember |
| No seeded credentials on the login page | A reviewer has to open the README | The assessment forbids exposing them in the production-facing interface, and a login form that fills itself in is a habit that ships |
| Honest placeholders | The dashboard looks empty | Every number would be invented. An invented number is a thing to be asked about in a review that nobody can defend |
| Self-hosted Inter | 344 KB of font in the repository | No third-party request on a page that handles credentials, no FOUT, no Google Fonts dependency at build time |

## The server/client line

`lib/auth.ts` imports `next/headers`, which exists only on the server.
Importing one value from it into a client component pulls it into the browser
bundle and fails the build - which is exactly what happened when the login
form imported `homePathFor` from there (D-13 in `AI_LOG.md`).

The module is now split along the real line:

| File | Holds | Usable from |
|---|---|---|
| `lib/auth-shared.ts` | types, `homePathFor` | both |
| `lib/auth.ts` | `cookies()`, `getCurrentUser`, `requireUser` | server only |

## Known limits

- **No dark mode.** The tokens are structured for it; nothing implements it.
- **No component tests.** The interaction checks are browser-verified and
  recorded with their measurements rather than automated. Playwright is worth
  it once there are forms with real consequences; at this size it would be
  ceremony.
- **`force-dynamic` on every protected route.** Correct here, and worth
  revisiting in F06 when some content genuinely is cacheable.
- **The drawer and menu depend on Radix's focus management.** If a future
  Radix release regresses, nothing here catches it. The behaviours are listed
  in the test matrix so they can be re-checked by hand.
