# F02.1 - Interview defence

Five questions a LIMAZ interviewer could reasonably ask after reading the
F02.1 code. Each attacks a decision actually made here.

---

## Q1 - Frontend authentication architecture

> Your auth check lives in a Server Component layout. Put it in Next
> middleware instead - it runs before the request reaches any page, it is one
> file, and it covers every route automatically. Why did you not?

**Because middleware can see that a cookie exists. It cannot see that the
cookie is valid.**

The session is a database-backed opaque token (F02). Deciding whether it is
real means asking the API, and middleware runs in an edge runtime where that
round trip is either unavailable or a latency cost on every single request
including static assets. So middleware ends up doing this:

```ts
if (!request.cookies.get('limaz_session')) return redirect('/login');
```

That check passes for `limaz_session=garbage`. It passes for a session that
was revoked a second ago by the logout in another tab. It passes for an
expired one. The page behind it still has to ask the API who the user is,
because it needs the name and the company to render - so the real check runs
in the layout **anyway**, and the middleware is a second, weaker copy of a
decision already being made.

Two checks that can disagree is worse than one. The one that can disagree in
the *permissive* direction is the one you delete.

What middleware is genuinely good at - cheap redirects on obviously
unauthenticated traffic - matters at a scale this service is not at, and it
would buy that at the price of a security story with two answers.

**The deeper point:** none of this is the security boundary. The API returns
401, 403 and 404 regardless of what the browser believes, and F02 proves every
one of those with no browser involved. If I deleted the layout check
entirely, nothing would become accessible - a person would just see an empty
frame instead of a login page. I would rather be asked why the routing is
"only UX" than claim it is protection.

**Backs it up:** `apps/web/app/(app)/layout.tsx`, `apps/web/lib/auth.ts`
(the comment says exactly this), F02 tests T13-T22, F02.1-T06.

## Q2 - Server state versus client state

> You used React Context for the user and no data-fetching library at all.
> Most teams reach for TanStack Query or SWR on day one. Is this not going to
> be rewritten the moment you add a second screen?

**No, because the Context here does not fetch anything. It carries a value the
server already resolved.**

That distinction is the whole answer. A server-state library solves cache
invalidation, request deduplication, background refetch, stale-while-
revalidate, mutation and rollback. In F02.1 there is exactly one value, it is
known before the first byte of HTML is sent, and it changes only by signing
out - which navigates. There is nothing to synchronise, so a synchronisation
library has no work to do and still costs a dependency, a provider, a cache
key convention and a loading state that is never true.

Using Context for *server* state is the anti-pattern people are warning
about - a `useEffect` that fetches into a Context, so every consumer re-renders
on every refetch and nothing knows when the data is stale. That is not this.
This is a prop drilled through a provider instead of six levels of components.

**It is not going to be rewritten - it is going to be joined.** F06 brings
expenses and reviews: lists that need caching, mutations that need
invalidation, a review decision that should roll back if the server rejects
it. That is real server state and TanStack Query arrives for it. The user
Context stays as it is, because resolving identity on the server is still the
right shape for identity.

Adopting the library in F02.1 to "get it out of the way" would mean writing a
`useQuery` for a value I already have, with an `initialData` that makes the
query a no-op, and a loading state that cannot occur. That is the dependency
paying nothing.

**Backs it up:** `apps/web/providers/auth-provider.tsx` (no fetch in it),
`docs/architecture/frontend.md` - the rejected-options table.

## Q3 - Responsive design decisions

> Your breakpoint is 1024px. Tailwind's `md` is 768 and that is where most
> people switch to a sidebar. And on mobile you scroll tables sideways, which
> everyone says is bad UX. Defend both.

**Both come from the same question: what is the content, and how narrow can it
get before it stops being readable.**

**1024 rather than 768.** The sidebar is 260px. At 768 that leaves roughly
500px of content, and the thing F06 puts in that space is an expense table with
amount, date, category, status and a decision control. 500px is not enough for
it, so at `md` I would ship a layout that is technically "desktop" and
practically unusable - the worst outcome, because it looks deliberate. 1024
minus 260 is 764px, which is a workable table. The breakpoint follows the
content rather than the convention.

**Horizontal scroll rather than hidden columns.** On an expense row, the
amount, the date and the decision are all essential - that is what the screen
is *for*. The usual mobile pattern is to hide secondary columns or collapse
each row into a card. Hiding is out: the assessment says directly not to hide
essential information to fit a smaller screen, and it is right, because a
reviewer approving an expense without the amount visible is a defect, not a
layout choice. Card collapse is a legitimate alternative, and it costs a
second rendering of every table plus a second set of bugs; I would reach for
it if the table grew past what sideways scroll can carry.

So: a controlled `overflow-x-auto` **container**, not a scrolling page. The
page never scrolls sideways - measured at 360, 390, 768, 1024, 1440 and 1920,
`scrollWidth` equals the viewport at each. Only the table scrolls, inside its
own box, which is the version of this pattern that does not feel broken.

**What I did not do:** choose the breakpoint by testing on my own screen. The
widths above are measured in a browser and recorded in the test matrix, because
"looks fine" is how 360px regressions ship.

**Backs it up:** `docs/architecture/frontend.md` (Responsive, Tables),
F02.1-T12, the width table in `docs/testing/F02.1-test-matrix.md`.

## Q4 - Component reusability

> You hand-wrote seven primitives and then pulled in Radix for two. That looks
> inconsistent. Either use a component library or do not.

**The line is not "hand-written versus library". It is whether the accessible
behaviour is non-trivial.**

A Button is a `<button>` with classes, a `disabled` state and `aria-busy`. A
Card is a `div` with a border. Writing those is minutes, and owning them means
no version upgrade can change how the application looks. Pulling a library for
them means inheriting its theming system, its bundle and its opinions to
avoid work I can do in an afternoon.

The drawer is different. To be usable it needs a focus trap, focus return to
the trigger on close, Escape, scroll lock, and the background marked inert for
assistive technology. Every one of those is easy to implement *almost*
correctly, and almost correct means a keyboard user is dropped behind an open
drawer with no way back. The dropdown menu needs roving arrow-key focus,
typeahead, Escape and `role="menu"` semantics. That is a real body of work
with a long tail of browser-specific bugs that other people have already
found.

So the rule is written down: **Radix only where the accessible behaviour is
non-trivial.** It is not inconsistent, it is a criterion, and a criterion is
what stops the next person from adding Radix for a tooltip or hand-rolling a
combobox.

The same reasoning rejected `clsx` and `tailwind-merge`. `lib/cn.ts` is six
lines. `tailwind-merge` exists to resolve conflicting utility classes arriving
from outside your control - a library passing `p-4` into a component you style
with `p-6`. Every call site here is ours, so that conflict does not exist, and
the dependency would be paying for a problem I do not have.

**The test of the rule:** it told me to verify, not assume. Drawer open →
`{ bodyScrollLocked: true, focusInsideDrawer: true }`; Escape →
`focusReturnedTo: "Open navigation menu"`. If Radix had not delivered that,
the reason for the dependency would have been gone.

**Backs it up:** `apps/web/components/layout/mobile-nav.tsx`,
`user-menu.tsx`, `apps/web/lib/cn.ts`, F02.1-T11 and T13.

## Q5 - Frontend authorization versus backend security

> Your sidebar hides the admin links from a manager, and `/admin` shows them
> an access-denied page. A manager can open DevTools and change their role in
> the Context in about ten seconds. What exactly has your frontend
> authorization achieved?

**Nothing, as security. It was never doing that job, and I would be worried
about an answer that claimed otherwise.**

If a manager edits the Context and makes the admin navigation appear, they can
click it. The page renders. Then it asks the API for companies and gets
`403` - because the API derives the role from the session row it looked up,
not from anything the browser sent. F02 proves that without a browser: T23 is
a manager hitting an admin-only route and getting 403, T26 is a cross-tenant
read getting 404.

Editing the frontend changes what a person sees. It cannot change what the
server does.

**So what is the hiding for?** Two things, both honest:

1. **Not showing people doors that will not open.** A manager who sees
   "Companies" and clicks it has learned that the application is confusing. A
   manager who does not see it has learned nothing wrong.
2. **Making the intended shape of the application visible** - the navigation
   marks unbuilt destinations with the feature that delivers them, rather than
   hiding them or linking to a 404.

**One deliberate detail:** a manager who reaches `/admin` gets a **page** that
says this area is for platform administrators, with a way back - not a silent
redirect. A silent bounce is indistinguishable from a broken link, and the
person is left guessing. The page costs nothing and leaks nothing: verified
that it renders no admin navigation and no other company's name.

**The asymmetry worth naming:** on the frontend, hiding is a courtesy. On the
backend, the choice between 403 and 404 is a security decision - 403 at row
level confirms a record exists, which is an enumeration oracle, so the API
returns 404 for a cross-tenant id and 403 only for role. That is ADR-003, and
it is the kind of decision the frontend never gets to make.

**Backs it up:** `apps/web/app/(app)/admin/layout.tsx`, `lib/nav.ts`,
ADR-003, F02 T23-T28, F02.1-T07 and T07b.
