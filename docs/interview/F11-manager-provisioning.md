# F11 - Interview defence

Five questions a LIMAZ interviewer could reasonably ask after reading the F11
code.

---

## Q1 - Administrator authorization

> You added a route that creates user accounts. What stops a company manager
> from calling it, and what stops a manager you created from creating more?

**Nothing new, and that is the answer.**

`@Roles('PLATFORM_ADMIN')` is on the `AdminController` **class**, so these two
routes inherited it the moment they existed. There is no new guard, no new
check, and no decorator anybody had to remember to add - which is the whole
reason the role lives on the class rather than on each method.

The refusals it produces are different for different callers, and the
difference is informative:

| Caller | Answer | Why |
|---|---|---|
| Company manager | 403 `insufficient_role` | A real person, a real session, the wrong role |
| Company API key | 403 `caller_type_not_allowed` | `@Roles` implies a human caller. A key has no role, so it can never satisfy one however valid it is |
| Unauthenticated | 401 | Resolved before authorization is asked |

A manager created by this feature is refused by the first row (F11-T16b).
There is no privilege ladder: the only role that can create accounts is the
one that cannot be created here.

**The honest caveat.** This is role-based, not permission-based. A platform
administrator can provision a manager for *any* company, and there is no
per-company administrator scope. That matches the assessment's model - one
platform admin, who manages every tenant - and it is a real limit if the
product ever grew resellers.

## Q2 - Safe password handling

> Why does the administrator type the password instead of the server
> generating one, when you already have the one-time-secret machinery for API
> keys?

**Because somebody has to carry the first password out of band either way, and
one of the two options puts a credential in a response that does not need to
be there.**

This deployment sends no email. So whichever way the password is produced, a
human hands it to another human. Given that:

| Generated by the server | Chosen by the administrator |
|---|---|
| Response carries a plaintext credential | Response carries **no credential** |
| Needs `Cache-Control: no-store`, a one-time reveal, a copy affordance | Needs none of it |
| A lost response leaves an account nobody can sign in to | The administrator already has the value |

The second has strictly fewer places for a secret to end up. There is no
`no-store` header on this route and that is deliberate: nothing in the
response is worth cache protection.

**What is reused rather than rebuilt:** `PasswordService`, the same one login
verifies against. A second hashing path would mean an account that cannot sign
in with the password it was created with.

**The two bounds, and why 72:** at least 12 characters, because this endpoint
*sets* policy for a new credential - unlike login, whose bound is loose so
that "too short" cannot confirm an address exists. At most 72 **bytes**,
because bcrypt hashes 72 and silently discards the rest. Accepting a longer
passphrase would create an account with far less entropy than the person
believes they set, and nothing would say so. Bytes rather than characters
because that is what bcrypt counts.

**What I did not build, and say so in the UI:** no reset, no change, no forced
change at first sign-in. Recorded as R-36.

## Q3 - Manager tenant assignment

> The request body has no `companyId` and no `role`. Suppose somebody sends
> them anyway.

**400, and nothing is created.**

`createManagerSchema` is `.strict()` and neither field is declared, so a body
carrying `"role": "PLATFORM_ADMIN"` is rejected at the parse rather than
ignored at the service.

The distinction is the point. "Ignored" is a property of **today's code**: it
holds only as long as nobody spreads the parsed object into
`prisma.user.create`. "Refused" is a property of the **schema**, and it holds
whatever the service does next. F11-T10 and F11-T11 assert both the 400 and
that `prisma.user.count` for that email is zero.

The two values that do end up on the row come from places the caller does not
control:

```
role      <- the literal 'MANAGER', written in ManagerAdminService
companyId <- the PATH parameter, after the role check
```

And the path parameter is a **selector**, not a proof - the same model the
API key routes use, and for the same reason: the guard already established
who is calling.

## Q4 - User identity and audit integrity

> You can create managers but not delete them. Is that an unfinished feature?

**No. Deleting one would break the record the assessment asks for.**

Section 5 requires "a record of who resolved each review, when, and how".
`Review.resolvedByUserId` is a foreign key onto `User` with
`onDelete: Restrict`, so the database refuses to remove an account that has
resolved anything. That is not an obstacle to work around - it is the
guarantee working.

The alternatives are all worse:

| Option | What it costs |
|---|---|
| Cascade the delete | The review loses its reviewer. The audit record becomes "somebody" |
| Null the reference | A CHECK constraint forbids a resolved review with no reviewer, and should |
| Soft-delete with a flag | A real design - and it needs a `status` column, a filter on every user query, and a decision about whether a deactivated manager's sessions die immediately. Out of F11's scope |

So the panel says it plainly: *"Accounts cannot be removed here, so a review
resolved by somebody who has left still names them."*

Deactivation is the feature actually wanted here, and it is a different one
from deletion. It is named as not built rather than implied.

## Q5 - Complete company onboarding

> Walk me through creating a working company from nothing. What was the gap
> before this, and how do you know it is closed?

**Four steps, all in the application:**

1. **Add a company** - creates the company, its policy and its first API key
   in one transaction. Each is meaningless without the others: no policy means
   submissions that cannot be decided, no key means a backend that cannot
   reach us.
2. **Add a manager** - now possible. Before F11 this step did not exist.
3. The backend submits expenses with the key.
4. The manager signs in and resolves what the policy flags.

**The gap** was step 2. The company detail page carried a warning saying the
company had no manager, what that meant, and that it was not automated. It was
honest and it was a dead end - a reviewer following the README had to insert a
database row to see the manager flow on a company they had just created.

**How I know it is closed** is the part worth defending, because a 201 is not
evidence. F11-T22 does the whole thing:

- creates a manager through the API
- signs in as that account
- submits an expense with the company's own API key, over its policy limit
- lets the **real** policy engine open the review
- resolves it as the new manager
- asserts in PostgreSQL that `resolvedByUserId` is the account that did not
  exist when the test started, that `resolvedAt` is set, and that the
  expense's `decision` is still `REVIEW` while its `status` is now `APPROVED`

That last assertion is the one I would point at. It shows the automated
decision is history and the human outcome is separate - and that a manager
provisioned minutes ago participates in the audit trail exactly like a seeded
one.

The same sequence was then driven through the browser, including the two
failure paths a reviewer will actually hit: a mixed-case email with
surrounding whitespace, and a duplicate address.
